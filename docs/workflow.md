# План работы с несколькими агентами и сравнение моделей

Ниже сначала поправки к замыслу (вы просили), потом конкретный порядок действий.

## 1. Что я бы изменил в замысле

1. **Два эксперимента смешаны в один.** «Разделить роли между агентами» и «сравнить модели на одной задаче» отвечают на разные вопросы. Если разные модели делают разные части одного сайта, то при плохом результате непонятно, виновата модель или стык между частями. Предлагаю так: каждая модель делает **весь сайт сама** (чистое сравнение), а роли разделены **вокруг** исполнителей: архитектор (этот пакет), исполнители, проверяющие. Разделение по частям сайта можно попробовать вторым, отдельным экспериментом.
2. **Нужны одинаковые условия.** Один пакет документов, один промпт (раздел 4), одни данные в `js/data.js`. Без этого вы сравниваете не модели, а то, что каждая из них выдумала про контакты и сорта кофе.
3. **В `main` исполнители не пишут.** Каждый работает в своей ветке и своей папке. ТЗ требует автодеплой `main` на Vercel, значит, в `main` должен попасть только победитель.
4. **Модель не оценивает собственную работу.** Оценка: скрипт `tools/check.py`, Lighthouse, ручной чек-лист и слепая оценка внешнего вида людьми. Модели склонны писать «всё готово, Lighthouse 95», не запустив его; в промпте стоит запрет.
5. **Классы моделей разные.** Судя по названиям, у вас «Flash» (быстрые, лёгкие) и «Max» (крупная). Сравнение честное по условиям, но не «модель против модели одного класса». Запишите уровень рядом с результатом. Я не знаю возможностей этих конкретных моделей, поэтому не угадываю победителя: рубрика покажет.
6. **Один прогон это анекдот, не статистика.** Вывод «модель X лучше» верен для этой задачи и этого запуска. Если останется время, повторите прогон для одной-двух моделей.
7. **«Красота» должна стать измеримой.** Раздел 6 переводит её в четыре критерия и слепую оценку.
8. **Срок.** До 15 ноября осталось 7 дней, это тоже ограничение эксперимента: фазы 0–2 за два дня, остальное на оценку и публикацию (раздел 7).

Спецификацию, архитектуру и задачи писал я (Claude). Я в сравнении не участвую, но мои решения общие для всех четырёх, это нейтрально для сравнения и может быть невыгодно любой из моделей, если она хуже работает с конкретным подходом (например, без фреймворков).

## 3. Git и Vercel

```
git checkout main && git pull
# положить пакет в репозиторий, затем:
git add . && git commit -m "T0.2: спецификация, данные, проверка" && git push

git branch impl/deepseek-v4-1-flash
git branch impl/codex-luna-6
git branch impl/gemini-3-8-flash
git branch impl/qwen-3-8-max
git push --all

# отдельная папка на каждую ветку, чтобы агенты не мешали друг другу:
git worktree add ../zerno7-deepseek impl/deepseek-v4-1-flash
git worktree add ../zerno7-codex    impl/codex-luna-6
git worktree add ../zerno7-gemini   impl/gemini-3-8-flash
git worktree add ../zerno7-qwen     impl/qwen-3-8-max
```

Каждого агента запускайте в **его** папке. Vercel для каждой ветки создаёт адрес предпросмотра. Для новых проектов он может требовать вход в аккаунт Vercel. Если так, либо отключите защиту предпросмотров в настройках проекта (раздел Deployment Protection), либо мерьте Lighthouse локально.

Идея: агенты работают в копиях, а вы собираете результаты. Если агент не умеет git, пусть просто меняет файлы в папке, коммиты сделаете вы.

## 4. Один и тот же промпт для всех

```
Ты разрабатываешь статический сайт кофейни и школы бариста «Зерно 7».
В репозитории уже есть ТЗ и проектные документы.

1. Прочитай AGENTS.md и документы, на которые он ссылается, по порядку.
2. Выполни задачи фаз 1–4 из docs/tasks.md в указанном порядке.
   Одна задача — один коммит, сообщение «<ID>: <что сделано>».
3. Факты бери только из js/data.js. Не придумывай цены, адреса, названия,
   имена, скидки. Если нужных данных нет, не заполняй выдумкой, а запиши
   пробел в README.md, раздел «Пробелы».
4. Работай только в этой ветке. Не меняй docs/tz.md и js/data.js.
5. Перед сообщением «готово» запусти python tools/check.py, приведи его
   вывод целиком и исправь все FAIL.
6. Если не можешь выполнить пункт (нет браузера для Lighthouse, нет доступа
   к картинкам), скажи об этом прямо. Не называй оценки и результаты,
   которые не измерял.
7. Добавь запись о своей работе в docs/prompts.md.
```

Одинаковая обратная связь для второго раунда: вы вставляете вывод `check.py` и список непройденных пунктов чек-листа раздела 6, больше ничего, без подсказок про дизайн.

## 5. Протокол прогона

Для каждой модели записывайте: название и уровень, в каком инструменте работала (чат, CLI, IDE), сколько времени заняла, сколько сообщений вы отправили, расход токенов или стоимость, использовала ли она браузер, что вы поправили руками. Это не в баллах, но без этого вывод «лучше» не имеет цены.

Условия: **один основной прогон и один раунд исправлений**, одинаково для всех.

## 6. Рубрика (100 баллов)

| Блок | Баллы | Как считается |
|---|---|---|
| A. Автопроверка | 30 | `check.py` сам печатает итог: 30 минус 1,5 за каждый провал (отсутствующая страница считается как 6), не ниже 0; WARN не считаются |
| B. Lighthouse главной, мобильный режим | 15 | По 5 баллов за каждый порог из ТЗ (Performance ≥ 70, Accessibility ≥ 90, SEO ≥ 90). Медиана трёх запусков, Chrome в режиме инкогнито |
| C. Функциональность | 25 | Чек-лист ниже, по 2,5 балла за пункт |
| D. Внешний вид | 20 | Слепая оценка |
| E. Тексты и честность | 10 | См. ниже |

**C. Чек-лист (10 пунктов).**

1. Меню: выделен пункт текущей страницы на всех страницах.
2. Тест: пять контрольных наборов из [quiz.md](quiz.md) дают указанные результаты.
3. Потоки: у потока без мест кнопка неактивна и не ведёт на форму.
4. Форма: без флажка не отправляется, флажок снят по умолчанию.
5. Форма: пустые обязательные поля показывают ошибки, при успехе открывается `thanks.html` с номером.
6. Предзаполнение: `contacts.html?course=latte-art&promo=LATTE10` выбирает курс и промокод.
7. Меню: все четыре фильтра работают, пустые дают понятное сообщение.
8. Промокод копируется, PDF скачиваются и открываются.
9. События из каталога появляются в `dataLayer`: проверить не меньше десяти из четырнадцати.
10. 404: неизвестный адрес на Vercel показывает `404.html`; на 375, 768 и 1280 px нет горизонтальной прокрутки.

**D. Внешний вид.** Снимки главной и одной внутренней страницы при 375 и 1280 px, названия моделей скрыты (A, B, C, D, порядок случайный). Не меньше трёх оценщиков, каждый ставит от 1 до 5 по четырём критериям: иерархия и композиция; типографика; цвета (фирменная палитра, контраст) и стиль; фотографии и ритм блоков. Баллы: среднее по оценщикам × 4.

**E. Тексты и честность.** 4 балла: нет выдуманных фактов (цены проверяет скрипт, остальное просмотром); 3 балла: термины поясняются при первом упоминании, тон на «вы»; 3 балла: README честно описывает пробелы, демо-места и то, что заявки не отправляются; за ложные утверждения агента о том, что он «проверил» (Lighthouse, события), минус до 3 баллов.

Отдельно, не в баллах: время, токены, стоимость, число ваших ручных правок.

## 8. Как вести журнал запросов в такой схеме

Запись в `docs/prompts.md` — это сообщение, которое **отправили вы**, а не внутренние шаги агента. В ветке исполнителя у агента своя запись о прогоне. В `main` в итоге: записи 001–002 (этот пакет) и записи победившей ветки плюс ваш раунд исправлений. Журнал честный: что получилось и что вы правили руками, в том числе если победитель потребовал вашей правки.
