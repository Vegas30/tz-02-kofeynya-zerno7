# План работы с несколькими агентами и сравнение моделей

Ниже сначала поправки к замыслу (вы просили), потом конкретный порядок действий.

## 1. Что я бы изменил в замысле

1. **Два эксперимента смешаны в один.** «Разделить роли между агентами» и «сравнить модели на одной задаче» отвечают на разные вопросы. Если разные модели делают разные части одного сайта, то при плохом результате непонятно, виновата модель или стык между частями. Предлагаю так: каждая модель делает **весь сайт сама** (чистое сравнение), а роли разделены **вокруг** исполнителей: архитектор (этот пакет), исполнители, проверяющие. Разделение по частям сайта можно попробовать вторым, отдельным экспериментом.
2. **Нужны одинаковые условия.** Один пакет документов, одна последовательность запросов (раздел 4), одни данные в `js/data.js`. Без этого вы сравниваете не модели, а то, что каждая из них выдумала про контакты и сорта кофе.
3. **В `main` исполнители не пишут.** Каждый работает в своей ветке и своей папке. ТЗ требует автодеплой `main` на Vercel, значит, в `main` должен попасть только победитель.
4. **Модель не оценивает собственную работу.** Оценка: скрипт `tools/check.py`, Lighthouse, ручной чек-лист и слепая оценка внешнего вида людьми. Модели склонны писать «всё готово, Lighthouse 95», не запустив его; в промпте стоит запрет.
5. **Классы моделей разные.** Судя по названиям, у вас «Flash» (быстрые, лёгкие) и «Max» (крупная). Сравнение честное по условиям, но не «модель против модели одного класса». Запишите уровень рядом с результатом. Я не знаю возможностей этих конкретных моделей, поэтому не угадываю победителя: рубрика покажет.
6. **Один прогон это анекдот, не статистика.** Вывод «модель X лучше» верен для этой задачи и этого запуска. Если останется время, повторите прогон для одной-двух моделей.
7. **«Красота» должна стать измеримой.** Раздел 6 переводит её в четыре критерия и слепую оценку.
8. **Срок.** По ТЗ сайт нужен к дню 4 от даты выдачи (раздел 9 ТЗ). В вашем экземпляре дата выдачи не заполнена. Если это сегодня, 8 ноября, то сайт нужен к 12 ноября: календарь в разделе 7 рассчитан на это.
9. **Картинки лучше дать всем одинаковые.** По Приложению А нужно около 25 изображений (первый экран, 6–8 фото класса, 5 шагов гида, 6 сортов, 3 преподавателя, OG). Не все агенты умеют генерировать картинки, и тогда вы сравнивали бы не вёрстку, а наличие картинок. Сделайте набор один раз (задача T0.6) и положите в `img/` до создания веток.
10. **Сайт это 15 баллов из 100.** Остальные 85 баллов даёт работа в GA4, Google Таблицах, ManyChat, DataLens и соцсетях ([scope-site.md](scope-site.md), раздел 1). Сравнение моделей не должно съесть время, которое потом понадобится там.
11. **Вы должны уметь объяснить код.** На приёмке заказчик выберет любой фрагмент из `js/`, и вы объясняете каждую строку. Поэтому код победителя нужно будет разобрать, и это входит в рубрику (блок F).


Спецификацию, архитектуру и задачи писал я (Claude). Я в сравнении не участвую, но мои решения общие для всех четырёх, это нейтрально для сравнения и может быть невыгодно любой из моделей, если она хуже работает с конкретным подходом (например, без фреймворков).

## 3. Git и Vercel

```
git checkout main && git pull
# положить пакет в репозиторий, затем:
git add . && git commit -m "T0.2: спецификация, данные, проверка" && git push

git branch impl/deepseek-v4-1-flash
git branch impl/codex-luna-6
git branch impl/gemini-3-8-flash
git branch impl/qwen-3-8-max
git push --all

# отдельная папка на каждую ветку, чтобы агенты не мешали друг другу:
git worktree add ../zerno7-deepseek impl/deepseek-v4-1-flash
git worktree add ../zerno7-codex    impl/codex-luna-6
git worktree add ../zerno7-gemini   impl/gemini-3-8-flash
git worktree add ../zerno7-qwen     impl/qwen-3-8-max
```

Каждого агента запускайте в **его** папке. Vercel для каждой ветки создаёт адрес предпросмотра. Для новых проектов он может требовать вход в аккаунт Vercel. Если так, либо отключите защиту предпросмотров в настройках проекта (раздел Deployment Protection), либо мерьте Lighthouse локально.

Идея: агенты работают в копиях, а вы собираете результаты. Если агент не умеет git, пусть просто меняет файлы в папке, коммиты сделаете вы.

## 4. Последовательность запросов (одинаковая для всех)

ТЗ (3.1) требует в журнале минимум: запрос на структуру, отдельный запрос на каждую страницу и запросы на исправления. Поэтому вместо одного большого промпта агент получает цепочку запросов. Один запрос это один коммит. Тексты ниже вы отправляете как есть, подставляя номер и страницу. Если агент работает в IDE или CLI, он видит файлы репозитория; если в чате, прикрепляйте `AGENTS.md`, `docs/architecture.md`, `docs/appendix-a.md` и `js/data.js`.

**R0. Структура.**

```
Ты разрабатываешь статический сайт кофейни и школы бариста «Зерно 7».
В репозитории уже есть ТЗ и проектные документы. Прочитай AGENTS.md,
docs/spec.md, docs/architecture.md, docs/scope-site.md.

Задача R0 — структура сайта. Создай каркас репозитория по
docs/architecture.md (раздел 2): css/tokens.css, css/base.css,
css/components.css (шапка, подвал, кнопки, карточка), js/analytics.js,
js/common.js и index.html только с <head>, шапкой, подвалом и пустым <main>.
Шапку и подвал бери по docs/appendix-a.md, данные из js/data.js.
Сделай один коммит «R0: структура сайта». Остальные страницы не создавай.
```

**R1–R9. Одна страница на запрос.** Порядок: R1 `index.html`, R2 `courses.html`, R3 `menu.html`, R4 `beans.html`, R5 `latte-guide.html`, R6 `contacts.html` (с `js/form.js`), R7 `thanks.html`, R8 `privacy.html`, R9 `404.html`.

```
Задача R<N> — страница <файл>. Сделай её по docs/appendix-a.md
(блоки и их порядок) и строке R<N> из docs/tasks.md.
<head>, шапку и подвал скопируй из index.html, меняя только title,
description, og-теги и aria-current. Данные бери только из js/data.js,
события описывай атрибутами data-event по docs/data-schema.md.
Соблюдай AGENTS.md. Другие страницы не трогай, кроме общих файлов,
если без этого не обойтись. Один коммит «R<N>: <файл>».
```

**R10. Контент.** «Подключи изображения из `img/` по `docs/images.md`, добавь `alt`, размеры, ленивую загрузку, подписи «Иллюстрация», поясни термины при первом упоминании на каждой странице. Один коммит.»

**R11. Документы.** «Создай PDF гида в `files/`, `docs/events.md` по `docs/data-schema.md` (раздел 3) и `README.md` по задаче Q4 из `docs/tasks.md`. Один коммит.»

**R12. Самопроверка.** «Запусти `python tools/check.py` и приведи вывод целиком. Ничего не исправляй.» Если запустить нечем, агент так и пишет.

**Раунд исправлений (одинаков для всех).** Вы вставляете вывод `check.py` и список непройденных пунктов чек-листа раздела 6, больше ничего, и пишете: «Исправь только эти замечания, по одному коммиту на группу. Запусти `check.py` снова и приведи вывод». Подсказок про дизайн нет.

Принципы для всех запросов (они зашиты в `AGENTS.md`): не придумывать факты, не сообщать результатов, которых не измеряли, писать простой комментированный JS.

**Турнир вместо полного прогона.** 12 запросов на 4 модели это около 50 отправок. Чтобы сэкономить время, пройдите R0 и R1 (структура и главная) со всеми четырьмя, оцените главную по рубрике (блоки B и D, быстрый A) и продолжайте R2–R12 только с двумя лучшими. Главная страница показывает внешний вид, а он и есть предмет сравнения. Остальные два результата сохраните как есть, без доработки.

## 5. Протокол прогона

Для каждой модели записывайте: название и уровень, в каком инструменте работала (чат, CLI, IDE), сколько заняла по времени, сколько сообщений вы отправили, расход токенов или стоимость, использовала ли браузер, что вы поправили руками. Это не в баллах, но без этого вывод «лучше» ничего не стоит.

Правила: запросы одинаковые для всех; **первый коммит с кодом это результат R0 без ваших правок** (требование ТЗ 3.4), правки руками делаются только в следующих коммитах и записываются в журнал.

## 6. Рубрика (100 баллов)

| Блок | Баллы | Как считается |
|---|---|---|
| A. Автопроверка | 30 | `check.py` сам печатает итог: 30 минус 1,5 за каждый провал (отсутствующая страница считается как 6), не ниже 0; WARN не считаются |
| B. Lighthouse главной, мобильный режим | 15 | По 5 баллов за каждый порог ТЗ (Performance ≥ 70, Accessibility ≥ 90, SEO ≥ 90). Медиана трёх запусков, Chrome в режиме инкогнито |
| C. Функциональность | 20 | Чек-лист ниже, по 2 балла за пункт |
| D. Внешний вид | 20 | Слепая оценка |
| E. Тексты и честность | 5 | См. ниже |
| F. Объяснимость JS | 10 | См. ниже |

**C. Чек-лист (10 пунктов).**

1. Меню: выделен пункт текущей страницы на всех страницах.
2. Тест: пять контрольных наборов из [quiz.md](quiz.md) дают указанные результаты; набор `0000` (испытание И-13) показывает курс, кнопку записи и вызывает `quiz_complete`.
3. Потоки: у потока без мест кнопка неактивна и не ведёт на форму.
4. Форма: без флажка не отправляется, флажок снят по умолчанию.
5. Форма: пустой телефон и телефон «123» дают ошибку у поля и событие `form_error` (испытание И-04); при верных данных открывается `thanks.html` с номером заявки.
6. Предзаполнение и UTM: `contacts.html?course=latte_art` выбирает курс; открыв `index.html?utm_source=test&utm_medium=social&utm_campaign=c&utm_content=x`, перейдя на форму и отправив её, в консоли в данных заявки видны те же метки.
7. Фильтр меню работает по всем четырём значениям (пустые дают понятное сообщение); промокод копируется; оба PDF скачиваются.
8. События: не менее 10 из 14 появляются в `dataLayer` с параметрами из каталога; `gtag('event'` встречается только в `js/analytics.js`.
9. Адаптив: на 375, 768 и 1280 px нет горизонтальной прокрутки (испытание И-01); неизвестный адрес на Vercel показывает `404.html`.
10. `thanks.html` без параметра показывает понятное сообщение, а не пустой номер.

**D. Внешний вид.** Снимки главной и одной внутренней страницы при 375 и 1280 px, названия моделей скрыты (A, B, C, D, порядок случайный). Не меньше трёх оценщиков, каждый ставит от 1 до 5 по четырём критериям: иерархия и композиция; типографика; цвета (фирменная палитра, контраст) и стиль; фотографии и ритм блоков. Баллы: среднее по оценщикам × 4.

**E. Тексты и честность (5).** 2 балла: нет выдуманных фактов (цены проверяет скрипт, остальное просмотром), термины поясняются, тон на «вы». 2 балла: README честно описывает пробелы, демо-режим формы. 1 балл: агент не заявлял непроверенных результатов (Lighthouse, события); за ложное заявление минус до 3 баллов из этого блока и из C.

**F. Объяснимость JS (10).** Берёте три случайных фрагмента по 20–30 строк из `js/`. Пытаетесь за 5 минут объяснить каждую строку (лучше, чтобы проверил кто-то другой). Оценка от 0 до 10 по тому, сколько строк объяснено без подсказки, плюс учёт: общий размер JS (цель до 600 строк), комментарии, понятные имена.

Отдельно, не в баллах: время, токены, стоимость, число ваших ручных правок.

## 8. Как вести журнал запросов в такой схеме

Запись в `docs/prompts.md` это сообщение, которое **отправили вы**, а не внутренние шаги агента. В начале файла: инструмент и версия (ТЗ 3.1). В `main` в итоге: записи 001–004 (этот пакет), записи победившей ветки (R0–R12 и раунд исправлений) и ваши правки руками. Если в сравнении участвовали другие модели, добавьте одну честную запись: «Запросы R0 и R1 отправлены ещё трём моделям для сравнения, результаты не использованы». Журнал честный: что получилось и что вы правили руками.
